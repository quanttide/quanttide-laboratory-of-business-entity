# p40 | 手册质量多维度评估

> 从叙事工程、知识工程、认知工程三个维度，系统评估量潮科技工作手册体系（docs/handbook）的内容质量与改进方向。

## 实验信息

| 属性 | 值 |
|------|-----|
| 编号 | p40 |
| 创建日期 | 2026-06-20 |
| 对应章程 | 无（元方法论实验） |
| 评估对象 | `default/quanttide-tech/docs/handbook/`（39 个职能目录） |
|| 状态 | 已实现（LLM 评估脚本） |

## 实验目的

已有一批"治理即代码"的 PoC（p01-p39）验证章程→代码的可行性。但手册本身的质量决定了这条管线的**上限**：

- 文本模糊→代码不确定→输出不可信
- 结构松散→知识难提取→自动化难落地
- 认知负载高→读者难理解→操作易出错

本实验提供一个系统的**手册质量诊断框架**，发现手册中的薄弱环节，驱动章程/手册/教程的三层改进闭环。

## 评估维度

### 一、叙事工程维度

评估手册**讲故事的效率**——是否让读者在最短时间内理解"这是什么、为什么要做、怎么做"。

#### 诊断指标

| 指标 | 含义 | 检查点 |
|------|------|--------|
| 场景锚定 | 是否以具体场景（而非抽象概念）开头 | 读者看完前三段能否复述一个具体工作场景？ |
| 角色代入 | 是否明确说明"谁是执行者、谁是审批者" | 手册中的"你"对应哪个岗位/角色？ |
| 因果闭环 | 是否说明"为什么这么做"而不只是"这么做" | 有没有"设计者注"或"设计理由"类的元注释？ |
| 反例教育 | 是否指出"典型错误做法" | 有没有"你不得做的事情"或"常见错误"？ |
| 叙事节奏 | 信息密度是否均匀，有无认知洼地 | 长段落是否有分节，关键规则是否突出？ |

#### 现行手册发现

**正面（举例：商务报价 `/handbook/business/quotation.md`）**

- ✅ 以场景开头（"场景一：收到报价需求"），而非定义解释
- ✅ 有"你不得做的事情"约束性条款
- ✅ 有"设计者注"元注释，解释设计理由
- ✅ 有客户分类表和人员等级表，角色代入清晰
- ⚠️ 人员等级表中有 3 个"（待补充）"，说明叙事中断

**负面（举例：软件工程 `/handbook/code/index.md`）**

- ❌ 仅 7 行，实质内容是"用 pyproject.toml 不用 requirements.txt，用 uv 代替 pip"——既无场景，也无角色，也无理由
- ❌ 标题"软件工程"却只覆盖 Python 工具选型，名不副实

**负面（举例：人力资源 `/handbook/human/index.md`）**

- ❌ 15 行，只有核心理念阐述，没有对"配置"的具体操作指南
- ❌ "培训与开发"指向外部手册，但未说明读者该何时查阅

---

### 二、知识工程维度

评估手册的**知识结构化程度**——知识是否可以被系统性地提取、索引、关联和复用（这也是"治理即代码"管线的输入质量）。

#### 诊断指标

| 指标 | 含义 | 检查点 |
|------|------|--------|
| 原子性 | 知识是否拆分为最小独立单元 | 一段话是否包含多个不相关的知识点？ |
| 可索引性 | 知识是否有清晰的检索入口 | 是否有 index.md？内容是否有唯一标识？ |
| 层级一致性 | 章节结构是否与知识层级匹配 | 标题深度是否反映知识点从属关系？ |
| 交叉引用 | 知识点之间是否有显式关联 | 是否有"详见X章"或"参照Y手册"？ |
| 版本对齐 | 手册是否引用了最新版本的章程/教程 | 引用的章程版本号是否与当前一致？ |

#### 现行手册发现

**正面**

- ✅ 大部分目录有 `index.md` 作为入口（业务、销售、人力资源等）
- ✅ 存在显式交叉引用（如销售手册引用 `channel.md`、`workflow.md`、`scripts.md`、`platforms.md`）
- ✅ `handbook/business/quotation.md` 引用了 `profile/business/quotation.md` 档案

**问题**

- ⚠️ 虽然大部分目录有 index.md，但索引内容深度不一：有的是完整导航（如销售），有的仅几句话（如人力资源）
- ❌ 没有全局 index.md 之外的交叉关联网络——39 个目录之间如何配合、职责边界在哪，缺乏系统化描述
- ❌ "（待补充）"标记在多个手册中出现——这是知识工程上的"空白节点"，会阻塞管线
- ❌ 代码手册（`/handbook/code/`）仅 7 行，作为 39 个子目录之一严重不平衡——知识碎片化

---

### 三、认知工程维度

评估手册的**认知负载**——读者阅读和执行手册是否需要消耗超出合理范围的心智资源。

#### 诊断指标

| 指标 | 含义 | 检查点 |
|------|------|--------|
| 工作记忆负担 | 一条操作需要记住多少上下文 | 操作步骤是否超过 7±2 项？是否需要同时对照多份文档？ |
| 决策歧义度 | 读者在哪个节点需要自己做判断 | 是否有"视情况而定"而无判断标准？ |
| 流程可见性 | 是否可在一页内看清完整流程 | 是否有流程图、时间线或检查清单？ |
| 异常路径覆盖 | 是否覆盖了常见异常和边界情况 | 是否有"如果...则..."的条件分支？ |
| 渐进披露 | 复杂知识是否分层呈现 | 是否有"新手必读"和"进阶参考"的区分？ |

#### 现行手册发现

**正面**

- ✅ 销售手册的"销售 vs 商务"对比表格——帮助读者快速建立认知模型
- ✅ 商务报价手册分场景呈现，每个场景有步骤编号——降低工作记忆负担
- ✅ "设计者注"在提供理由的同时，也是一种"解释为什么规则如此"的认知支持

**问题**

- ❌ 人力资源手册的 index.md 只有理念阐述，无操作入口——读者看完不知道下一步该做什么
- ❌ 39 个目录没有统一的"入口地图"——新员工面对 39 个目录不知道该从哪里开始
- ⚠️ 异常路径覆盖仅在商务报价手册中有初步体现（"你不得做的事情"），其他手册普遍缺失
- ⚠️ 没有"新手路径"和"专家路径"的分层——所有内容平铺，对新人不友好

---

## 总结：手册体系健康度

将评价分为三个等级：

| 等级 | 含义 | 覆盖范围 |
|------|------|----------|
| 🟢 健康 | 叙事清晰、知识结构化、认知负载合理 | 商务报价、销售（约 3-5 个手册） |
| 🟡 亚健康 | 存在明显缺口但有改进路径 | 大部分手册（约 25-30 个） |
| 🔴 不健康 | 内容严重不足或结构混乱 | 软件工程、部分新手册（约 5-10 个） |

### 核心发现

1. **文本可编码性不是唯一标准**——即使"治理即代码"管线能提取知识，被提取的知识质量取决于手册本身的叙事、结构和认知设计
2. **"设计者注"是高质量信号**——有"设计者注"的手册（如商务报价）通常在其他维度也表现更好，它说明作者在写作时已有元认知
3. **手册"冷热不均"**——商务扩展、销售等面向客户的手册质量较高，而内部职能（软件工程、人力资源）的手册质量偏低，这与使用频率和外部压力正相关
4. **`index.md` 是认知入口，不应是敷衍之物**——部分 index.md 只有几句话，没有发挥导航作用

## 改进建议

### 短期（可立即执行）

- 补充所有"（待补充）"标记
- 为每位手册添加"设计理由"或"设计者注"（叙事工程）
- 完善 index.md，统一格式（方案阐述 + 文件索引 + 阅读顺序建议）

### 中期

- 为每个手册添加"异常路径"章节（认知工程）
- 建立手册之间的交叉引用矩阵（知识工程）
- 添加"新手 15 分钟"和"老手速查"两种阅读路径（认知工程）

### 长期

- 将叙事工程、知识工程、认知工程加入手册编写规范（CONTRIBUTING.md）
- 开发"手册质量自动检查"脚本，扫描三个维度的指标
- 将手册质量作为章程修订的输入——"手册写不清楚的规则就是模糊的章程"

## 实现方案

### LLM 评估脚本

**文件：** `examples/p40-evaluate.py`

使用 DeepSeek V4（`deepseek-chat`）对每个手册文件评估 15 个指标（叙事 5 + 知识 5 + 认知 5）。

**工作流程：**

```
读取 handbook/*.md → 对每个文件调用 LLM → 5 个指标/维度 → 结构化 JSON → 汇总报告
```

**命令：**

```bash
# 完整评估（88 个文件，~22 分钟）
python3 examples/p40-evaluate.py

# 快速模式：仅评估 index.md
python3 examples/p40-evaluate.py --quick

# 测试模式：仅评估前 5 个文件
python3 examples/p40-evaluate.py --limit 5

# 断点续评（中断后继续）
python3 examples/p40-evaluate.py --resume
```

**输出：**
| 文件 | 格式 | 内容 |
|------|------|------|
| `p40-results.json` | JSON | 每个文件 15 个指标的评分 + 评审理由 + 证据摘录 |
| `p40-report.md` | Markdown | 健康度总览 + 维度分析 + 文件排行 + 改进建议 |

**单次 LLM 调用产出：**

```json
{
  "score": 4,
  "reason": "以具体场景开头，有清晰的角色定义",
  "evidence": "「场景一：收到报价需求，初步评估」"
}
```

### 架构说明

```
evaluate.py
├── get_all_handbook_files()   → 扫描 handbook 下所有 .md（排除元文件）
├── evaluate_file()            → 对单个文件调用 15 次 LLM
├── call_llm()                 → DeepSeek V4 API 调用（带重试）
├── parse_score_response()     → JSON 解析 + 容错
├── compute_stats()            → 维度平均/健康度分布/排行
└── generate_markdown_report() → 生成可读报告
```

每次评估后自动保存中间结果（`p40-results.json`），支持断点续评。
