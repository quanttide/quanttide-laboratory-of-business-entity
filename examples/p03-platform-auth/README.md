# p03: 平台权限体系（君主立宪制映射）

验证创始人特权模型投射到软件平台的可行性与设计方案。

## 映射关系

| 治理概念 | 平台映射 | 实现要点 |
|----------|----------|----------|
| 创始人特权 | 超级管理员（Super Admin） | 拥有全部权限，未显式授权的默认归 super admin |
| 权力让渡 | RBAC 角色授权 | 日常操作下放给普通角色，可撤回 |
| 上议院（独立司法权） | 高级审批角色 | 在专属权限内独立决策，不经审批流 |
| 下议院（独立立法权） | 普通角色自主操作 | 在授权范围内自行执行 |
| 上议院（立法流程） | 高级审批节点 | 标准事项逐级上报到此 |
| 下议院（立法流程） | 流程发起者 | 标准事项从此发起 |
| 直接行使 | Break-glass 机制 | 紧急绕过，无审批链，触发即执行，记录留痕 |
| 不得委托 | 操作不可转授权 | 超管操作须本人执行 |
| 书面记录 | 审计日志 | 区分"独立执行"、"经审批"和"直接执行"三种记录类型 |

## 核心原则

### 1. 剩余权限原则

> 未显式授权给角色的权限，默认归 Super Admin。

与 RBAC 的"最小权限原则"不同，剩余权限原则是逆向的：角色拿到的是显式授予的操作权，未被授予的全归 Super Admin。这确保新功能上线时默认只有超管可用，需经显式授权才下放。

### 2. 让渡可进化

> 随着角色成熟，逐步扩大让渡范围。

系统应支持权限粒度的渐进式下放，而非一次性全量授权。例如：新业务线初期只有超管能审批，成熟后下放给该业务线的审批角色。

### 3. 三轨审计

> 三种运行模式产生不同审计日志。

| 模式 | 审计日志特征 |
|------|-------------|
| 独立行使 | 角色 + 操作 + 结果，无审批链 |
| 经立法流程执行 | 包含完整审批链：发起人 → 逐级审批 → 执行人 → 结果 |
| 直接执行（Break-glass） | 包含触发原因 + 执行人 + 依据 + 结果，无审批链 |

### 4. Break-glass 约束

- 必须有明确的触发条件（如审批超时、紧急故障）
- 执行后自动通知相关方
- 事后审计不可篡改

## 验收标准

- [ ] 剩余权限原则可在权限模型中实现：未授权=默认拒绝给非超管
- [ ] RBAC 支持权限的渐进式下放和撤回
- [ ] 审批流支持双向（逐级上报 / 高级发起）
- [ ] Break-glass 机制有触发条件、执行记录、事后通知
- [ ] 审计日志区分两条路径，且记录格式一致可串联
- [ ] 超管操作不可转授权
