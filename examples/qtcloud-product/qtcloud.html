一、领域模型清单

一个空间、一条河床、一份工作物：空间拥有工作物与工作流，工作流编排任务并引用工作物，任务的修订提案经验收闸门合入工作物。

工作空间 Workspace

  • name / goal / boundary
  • 拥有 Doc 与 Workflow，空间之间保持独立

围绕一个上下文组织工作的容器

工作流 Workflow

  • tasks: Task[]，artifact: Artifact 引用
  • isReady 就绪判定 / readyCloudTasks 自动衔接对象
  • approve 验收闸门 / dispatchIntent 意图派活

河床：调度语义与验收闸门都在这里

任务 Task

  • 状态机：待办 → 执行中 → 待验收 → 完成；驳回是唯一回流
  • executor（用户 / 某朵云）、dependsOn（DAG 依赖）
  • output: Change[] 产出提案、deliverable、review 驳回意见

人机同构——人和云走同一套任务协议

工作物·文档 Doc（Artifact 实现）

  • title / version / sections / revisions
  • apply(changes) 合入修订：章节正文更新，版本 +1，版本轴留痕

「当前有效口径」的唯一载体

章节 DocSection

  • id（寻址键）/ title / text
  • Change.target 解析为章节 id

版本刻度 Revision

  • version / taskId / taskName / executor / time
  • 每次验收合入形成一个刻度，最新在前

记录「当前有效口径」怎么一步步来的

修订提案 Change（值对象）

  • target（章节 id）/ before / after
  • before 为空 = 章节末尾追加

对工作物内可寻址对象的修改，验收通过即合入

日志段落 JournalSection

  • group（来源群，即寻址键）/ start / end / text / topic
  • section 映射为 DocSection；同一群同日合并 = 段落末尾追加

journal 平台化：一个来源群一个段落

红线自检 RedLineChecker（策略服务）

  • 飞书 ID（oc_/ou_/on_）、内部链接、经营敏感词
  • 真实姓名清单由平台侧注入，映射表不入仓库

agent 自律收编为平台强制检查，人工兜底在验收闸门

二、模型关系

关系从 → 到语义代码落点
拥有Workspace → Doc、Workflow空间是容器，工作物与工作流归属空间Workspace 构造参数
引用（不拥有）Workflow → Artifact工作流只依赖抽象，不依赖具体工作物类型Workflow.artifact
编排（1 → n）Workflow → Task任务按依赖组成 DAG，调度与闸门在工作流上Workflow.tasks
依赖（n → n）Task → TaskdependsOn 构成 DAG，上游全部验收才就绪Task.dependsOn / isReady
提案（1 → n）Task → Change任务产出修订提案，验收通过即合入Task.output
寻址Change → DocSectiontarget 解析为章节 id；before 为空 = 末尾追加Doc.apply
合入 → 留痕Change → Doc → Revision验收闸门合入修订，版本 +1 并记一个刻度Workflow.approve / Doc.apply
成稿映射JournalSection → DocSection日志段落即章节文档的一段，寻址键为来源群JournalSection.section

三、事件风暴

按两条业务流回放：方案协作（demo 已实现）与日志更新平台化（本轮新收编，红色虚线部分依赖连接器落位）。

流 A · 方案协作（已实现）

人只在闸门出现，其余衔接由河床规则自动推进——每次自动衔接都指认「原为人工搬运」。

用户说一句话 → 派活 dispatchIntent意图库匹配，听不懂返回 null → Workflow新建任务入 DAG → 任务已创建pending，挂上依赖
就绪判定 isReady待办 且 上游全部验收通过 → 自动衔接 readyCloudTasks就绪且执行者是云 → 开工 Task.start → 任务已开工pending → running · 原为人工派单
交付 Task.deliver云自动交付；人的任务须填交付说明 → 修改已交付running → reviewing → 内联 diff 读模型红删绿增，验收有对象
用户在闸门拍板 → 验收通过 approve → Doc.apply合入 Change，版本 +1 → 修改已合入 · 版本已递增reviewing → done · 章节正文更新 → 版本刻度已记录Revision 入版本轴，版本号不撒谎
用户驳回须写意见 → 驳回 Task.reject(note) → 任务已驳回reviewing → running（唯一回流）· 方案一字不动 → 按意见修改后重新交付云任务自动改稿重交

流 B · 日志更新平台化（新收编，DAG：拉取 → 成稿 → 脱敏验收 → 写回）

fetch-chat-logs 技能的平台化收编：流程已验证，只做收编不改写法。红线从 agent 自律变为闸门前的平台强制检查。

用户「更新今天的日志」 → 派活 · 日志分支 dispatchIntent意图库新增分支 → 日志流程已派发四步 DAG 编排完成
日志云lark-cli 能力收编 → 拉取群消息按群名解析 chat_id，不落库 → 群消息已拉取时段正序 · 翻页到 has_more 为止
来源群分流 journalLineFor实训基地→qtclass · 闲聊水库→按内容 · 兜底 default → 分流成稿事实 + 原话，一个来源群一段 → JournalSection同日已有文件 = 向同一段落追加 → 段落已成稿Change 寻址：target = 来源群
红线自检 RedLineChecker.checkoc_/ou_ ID · 飞书链接 · 敏感词 · 平台侧注入姓名 → 红线已命中拦在闸门之前，打回成稿 → 红线已通过进入人工验收
用户脱敏验收：对照红线检查内联 diff → 验收通过 / 驳回 approve / reject → Doc.apply日志文档合入段落 → 日志修改已合入驳回则 journal 一字不动
日志云 → 写回 journal serializeJournal来源行 + 章节标题带群名时段 → 日志已写回 · 指针已同步journal 仓库提交 + 主仓库指针
