# 执行方案 — 知识库质量反向检测

## 检测维度

| 维度 | 检测内容 | 检测方式 | 反馈给人类 |
|------|---------|---------|-----------|
| **知识建模** | AI 能否从知识库中提取出清晰的概念模型、关系模型和规则模型？模型是否有歧义、冗余或缺失？ | 自动抽取知识图谱 / 本体模型，评估模型清晰度与覆盖度 | 展示抽取出的模型结构，标记模糊或断裂处 |
| **知识融合** | 不同来源、不同表述的知识在融合后是否一致？是否存在同名异义、异名同义、矛盾断言？ | 实体对齐、冲突检测、冗余检测 | 列出冲突项和冗余项，标注置信度 |
| **结构自洽性** | 知识库是否有自我引用的规则？规则之间是否冲突？ | 元规则匹配 | 高亮矛盾规则对 |
| **规范遵循度** | 知识是否遵循自身声明的写作规范？ | 样式一致性扫描 | 定位违规段落 |
| **完备性** | 必备的结构要素是否缺失？ | 模板匹配 | 列出缺失要素清单 |

## 执行阶段

检测按三个阶段依次推进，后一阶段依赖前一阶段的输出。

### 第一阶段：元规则提取

**目标**：从知识库中提取"知识应该怎么写"的元规则，作为后续检测的基准。

**步骤**：

1. **规则文件识别**：扫描目录下所有 `.md` 文件，识别以下三类元规则载体：
   - **章程类**：文件名包含 `章程`、`bylaw`、`charter`，内容有条款式规则（应当/不得/可以）
   - **规范类**：文件名包含 `格式`、`format`、`style`、`规范`，内容定义排版和结构标准
   - **自描述类**：`AGENTS.md`、`CONTRIBUTING.md`，内容定义工作方法和约束

2. **规则提取**：对识别出的元规则文件，逐条提取规则，格式化为 `(规则ID, 规则类型, 约束对象, 约束条件, 规范值)`：
   - **规则类型**：`STRUCTURE`（结构要求）、`FORMAT`（格式要求）、`LANGUAGE`（用语要求）、`CONTENT`（内容要求）
   - **示例**：从 docs-format.md 第五条提取 `(DF-005, FORMAT, 全文, 格式元素数量, 最小必要范围)`
   - **示例**：从 write-bylaw.md 第十二条提取 `(WB-012, CONTENT, 总则, 必备条款, [制定依据, 目的, 适用范围, 定义])`

3. **规则图谱构建**：建立规则之间的引用和约束关系图，标记：
   - 重复规则（不同文件规定了同一件事）
   - 矛盾规则（对同一对象的约束条件冲突）
   - 孤立规则（没有被任何知识条目引用的规则）

**输出**：元规则清单 + 规则关系图 + 规则矛盾预警

---

### 第二阶段：维度检测

**目标**：基于第一阶段提取的元规则，对知识库执行五个维度的检测。

检测执行顺序：**完备性 → 规范遵循度 → 结构自洽性 → 知识建模 → 知识融合**。前三个为格式检测，后两个为语义检测。

#### 2.1 完备性检测

对照元规则中定义的模板结构，逐文件检查必备要素是否缺失。

**检测规则**：

| 检查项 | 规则来源 | 检测逻辑 |
|--------|---------|---------|
| 总则必备条款 | write-bylaw 第十二条 | 检查总则章节是否包含制定依据、目的、适用范围、定义 |
| 附则必备条款 | write-bylaw 第十三条 | 检查附则章节是否包含章程效力、解释权 |
| 标准框架遵循 | write-bylaw 第五条 | 检查文档结构是否匹配 总则→主体→附则 框架 |
| 标题层级克制 | docs-format 第八条 | 检查是否超过三级标题嵌套 |
| 文件命名规范 | write-bylaw 第十九条 | 检查文件名是否使用 snake_case |

**输出**：`(文件, 缺失要素, 规则引用, 建议操作)`

#### 2.2 规范遵循度检测

对照元规则中定义的格式和语言规范，逐文件扫描违规情况。

**检测规则**：

| 检查项 | 规则来源 | 检测逻辑 |
|--------|---------|---------|
| 规范用语一致性 | write-bylaw 第十六条 | 检查应当/不得/可以等用语是否混用 |
| 分隔线滥用 | docs-format 第十条 | 统计分隔线使用次数，>3 处记为警告 |
| 加粗滥用 | docs-format 第十七条 | 检查非术语定义处的加粗使用 |
| 列表嵌套过深 | docs-format 第十一条 | 检查列表嵌套是否超过两级 |
| 时效性表述 | write-bylaw 第九条 | 扫描"当前""下一步""近期"等词汇 |
| 口语化表述 | write-bylaw 第十五条 | 扫描对话式、情感化表达 |

**输出**：`(文件, 行号, 违规类型, 当前值, 期望值, 规则引用)`

#### 2.3 结构自洽性检测

检查知识库内部的规则引用和定义是否自洽。

**检测规则**：

| 检查项 | 检测逻辑 |
|--------|---------|
| 规则自引用 | 是否存在 A 规则引用自身作为依据 |
| 规则循环 | 规则 A 引用 B，B 引用 C，C 引用 A 的循环链路 |
| 定义一致性 | 同一术语在不同文件中定义是否一致 |
| 条款编号连续性 | 条款编号是否连续无跳跃 |
| 交叉引用有效性 | 引用其他条款或文件的链接是否有效 |

**输出**：`(规则对, 冲突类型, 冲突描述, 影响范围)`

#### 2.4 知识建模检测

从知识库中抽取概念、关系和规则模型，评估模型质量。

**检测规则**：

| 检查项 | 检测逻辑 |
|--------|---------|
| 概念抽取 | 提取加粗术语和定义句，构建概念清单 |
| 关系抽取 | 识别概念间的 is-a、part-of、causal 等关系 |
| 未定义概念 | 标记使用了但未定义的术语 |
| 孤立概念 | 标记没有与其他概念关联的孤立节点 |
| 循环定义 | 检测定义链中是否存在 A 依赖 B、B 依赖 A |

**输出**：知识模型图 + `(概念, 问题类型, 上下文)`

#### 2.5 知识融合检测

跨文件检测知识的融合质量。

**检测规则**：

| 检查项 | 检测逻辑 |
|--------|---------|
| 同名异义 | 相同术语在不同文件中含义不同 |
| 异名同义 | 不同术语指代同一概念 |
| 矛盾断言 | 对同一属性在不同文件中有矛盾声明 |
| 冗余定义 | 同一概念在多处重复定义 |
| 引用断裂 | 跨文件引用指向不存在的章节或条款 |

**输出**：`(实体A, 实体B, 冲突类型, 置信度, 来源文件)`

---

### 第三阶段：交叉分析与报告生成

**目标**：将五个维度的检测结果进行交叉分析，生成综合质量报告。

#### 3.1 交叉分析

| 交叉维度 | 分析内容 | 输出 |
|---------|---------|------|
| 完备性 × 规范遵循度 | 缺失要素集中的文件是否也存在更多格式违规 | 质量薄弱文件排名 |
| 结构自洽性 × 知识建模 | 自洽性问题是否导致概念模型中的矛盾 | 规则—概念矛盾映射 |
| 知识融合 × 完备性 | 融合检测发现的冗余是否由模板缺失导致 | 根因分类 |

#### 3.2 严重级别评定

```
违规评级：
  P0 — 阻断性：元规则自相矛盾、必备条款缺失，须立即修改
  P1 — 严重：概念未定义、同义冲突，建议本轮修改
  P2 — 一般：格式违规、用语不一致，可推迟修改
  P3 — 建议：冗余定义、样式微调，可纳入后续迭代
```

#### 3.3 质量评分

每个维度独立评分（0–100），按权重汇总：

| 维度 | 权重 | 评分逻辑 |
|------|------|---------|
| 完备性 | 25% | 必备要素缺失率扣分 |
| 规范遵循度 | 20% | 每千字违规数 |
| 结构自洽性 | 20% | 矛盾规则对数 |
| 知识建模 | 20% | 未定义概念比率 |
| 知识融合 | 15% | 冲突/冗余条目数 |

---

### 第四阶段：人机交互闭环

检测以交互式方式执行，每阶段完成后暂停等待人类确认。

**执行流程**：

```
[第一阶段] 元规则提取完成
   ↓ 展示规则清单和矛盾预警 → 等待人类确认/修正规则
[第二阶段] 维度检测执行
   ↓ 按 2.1→2.5 顺序执行，每项完成后展示结果摘要
[第三阶段] 交叉分析与报告生成
   ↓ 展示综合报告 → 等待人类评审
[第四阶段] 问题追踪
   ↓ 记录已确认/已修复问题 → 支持增量检测
```

#### 问题追踪表

每次检测生成一份问题追踪表，格式：

```json
{
  "issue_id": "Q-001",
  "file": "sample/write-bylaw.md",
  "line": 45,
  "dimension": "completeness",
  "severity": "P1",
  "rule": "WB-012",
  "description": "总则缺少'定义'条款",
  "suggestion": "新增第四条'定义'，对本章程使用的关键术语作出界定",
  "status": "confirmed",
  "confirmed_at": "2025-01-01",
  "fixed_at": null
}
```

#### 增量检测

在问题追踪表基础上，后续检测只扫描：
1. 新增文件
2. 有修改的文件
3. 与前次检测结果存在关联的问题
