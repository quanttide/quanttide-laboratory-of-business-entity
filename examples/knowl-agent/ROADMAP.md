# 执行方案 — 知识库质量反向检测

## 检测维度

| 维度 | 检测内容 | 检测方式 | 反馈给人类 |
|------|---------|---------|-----------|
| **知识抽取** | 能否从知识文本中抽取出结构化知识要素（实体、关系、属性、规则、术语定义）？ | NLP 解析 + 模式匹配，从文本中提取知识三元组和定义句 | 展示抽取出的知识要素清单，标记未解析段落 |
| **知识建模** | 抽取出的知识能否构成清晰、一致、完备的概念模型和规则模型？模型是否有歧义、冗余、循环或缺失？ | 构建知识图谱 / 本体模型，分析模型结构质量 | 展示模型结构图，标记模糊、断裂、孤立、循环处 |
| **知识融合** | 不同文件的知识在融合后是否一致？是否存在同名异义、异名同义、矛盾断言、冗余定义？ | 跨文件实体对齐、冲突检测、冗余检测 | 列出冲突项和冗余项，标注置信度和来源 |

## 执行阶段

按三个阶段依次推进，后一阶段依赖前一阶段的输出。

### 第一阶段：知识抽取

**目标**：从知识库所有文件中抽取出结构化的知识要素。

#### 1.1 术语与定义抽取

| 检查项 | 检测逻辑 |
|--------|---------|
| 定义句识别 | 提取 `**Xxx**，指` / `**Xxx**，是` / `称为 Xxx` 等定义模式 |
| 加粗术语提取 | 提取所有加粗标记的术语，关联其上下文 |
| 条款标题提取 | 提取每一条款的标题和摘要内容 |

#### 1.2 实体与关系抽取

| 检查项 | 检测逻辑 |
|--------|---------|
| 实体识别 | 识别章节标题、条款主题中的核心实体（业务域、岗位、流程、文件等） |
| 关系抽取 | 识别实体间的 `is-a`、`part-of`、`regulated-by`、`depends-on`、`produces` 等关系 |
| 属性抽取 | 提取实体的属性声明（如"职权由五项权能构成"中的五项） |
| 规则抽取 | 提取 `应当/不得/可以` 引导的规范语句，结构化为 `(条件 → 规范行为)` |

#### 1.3 输出格式

```json
{
  "terms": [
    { "id": "T-001", "name": "工作订单", "definition": "经双方签署的就具体服务项目、服务范围、交付物等约定的书面文件", "source": "qtdata-index.md:18" }
  ],
  "entities": [
    { "id": "E-001", "name": "项目经理", "type": "role", "source": "qtdata-index.md:50" }
  ],
  "relations": [
    { "subject": "E-001", "predicate": "regulated-by", "object": "T-001", "source": "qtdata-index.md:59" }
  ],
  "rules": [
    { "id": "R-001", "condition": "员工提出辞职", "action": "应当提前三十日书面通知", "source": "human-resignation.md:34" }
  ]
}
```

### 第二阶段：知识建模

**目标**：基于抽取结果构建模型，评估模型的结构质量。

#### 2.1 概念模型评估

| 检查项 | 检测逻辑 |
|--------|---------|
| 未定义概念 | 标记使用了加粗或作为核心术语但缺少定义句的术语 |
| 孤立节点 | 标记没有任何关系关联的实体 |
| 循环定义 | 检测定义链中 A 依赖 B、B 依赖 A 的循环 |
| 概念层级 | 评估 is-a 层级的深度和覆盖度 |
| 定义清晰度 | 检查定义句是否包含自指或同语反复 |

#### 2.2 规则模型评估

| 检查项 | 检测逻辑 |
|--------|---------|
| 规则完备性 | 同一个规范主题是否既有义务性规则又有授权性规则 |
| 规则冲突 | 同一实体在不同条款中被赋予矛盾的义务/授权 |
| 规则悬挂 | 规则引用了不存在的实体或概念 |
| 例外缺失 | 强制性规则是否缺少例外条款 |

#### 2.3 输出格式

```json
{
  "model_issues": [
    {
      "id": "M-001",
      "type": "undefined_term",
      "term": "认知主权",
      "context": "connect-index.md:15",
      "severity": "P1",
      "suggestion": "在总则中增加'认知主权'的定义条款"
    }
  ],
  "model_stats": {
    "total_entities": 45,
    "total_relations": 78,
    "undefined_terms": 3,
    "isolated_nodes": 1,
    "circular_definitions": 0,
    "rule_conflicts": 0
  }
}
```

### 第三阶段：知识融合

**目标**：跨文件检测知识的一致性，输出冲突报告。

#### 3.1 对齐与冲突检测

| 检查项 | 检测逻辑 |
|--------|---------|
| 同名异义 | 相同术语在不同文件中定义不同 |
| 异名同义 | 不同术语指向同一概念（如"代表"和"公司代表"） |
| 矛盾断言 | 对同一实体的同一属性在不同文件中有矛盾声明 |
| 冗余定义 | 同一概念在多处重复定义且内容一致（浪费） |
| 引用断裂 | 跨文件引用指向不存在的章节、条款或文件 |
| 层级冲突 | 同一实体在不同文件中被赋予不同的类型或归属 |

#### 3.2 输出格式

```json
{
  "fusion_issues": [
    {
      "id": "F-001",
      "type": "same_name_diff_meaning",
      "term": "章程",
      "context_a": "write-bylaw.md:15（治理文件）",
      "context_b": "connect-index.md（未明确定义）",
      "severity": "P2",
      "suggestion": "统一'章程'的定义，或在各文件中显式引用 write-bylaw 的定义"
    }
  ],
  "fusion_stats": {
    "alignment_pairs": 35,
    "conflicts": 1,
    "redundancies": 2,
    "broken_refs": 0
  }
}
```

### 第四阶段：报告与追踪

#### 4.1 严重级别

```
P0 — 阻断性：循环定义、模型断裂，须立即修复
P1 — 严重：未定义概念、同义冲突，建议本轮修复
P2 — 一般：冗余定义、孤立节点，可推迟处理
P3 — 建议：模型覆盖度不足，可纳入后续迭代
```

#### 4.2 问题追踪

每次检测生成 `data/issues.json`，每条记录：

```json
{
  "issue_id": "Q-001",
  "phase": "modeling",
  "type": "undefined_term",
  "file": "sample/connect-index.md",
  "line": 15,
  "severity": "P1",
  "description": "术语'认知主权'使用但未定义",
  "suggestion": "新增'认知主权'的定义条款",
  "status": "open",
  "created_at": "2025-05-19",
  "fixed_at": null
}
```

#### 4.3 增量检测

后续检测只扫描：
1. 新增文件
2. 有修改的文件
3. 与前次检测结果存在关联的问题
