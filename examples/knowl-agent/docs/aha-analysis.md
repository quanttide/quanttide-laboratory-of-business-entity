# Aha 时刻分析：效力声明的不一致

## 发现

融合报告发现一个矛盾断言：六份章程的效力声明使用了不同的生效主体。

| 文件 | 效力声明 | 生效主体 |
|------|---------|---------|
| docs-format.md | 经公司最高权力机构审议通过后生效 | 最高权力机构 |
| company-representative.md | 经公司最高权力机构审议通过后生效 | 最高权力机构 |
| human-resignation.md | 经公司最高权力机构审议通过后生效 | 最高权力机构 |
| connect-index.md | 经公司最高权力机构审议通过后生效 | 最高权力机构 |
| write-bylaw.md | 经公司治理机构审议通过，自发布之日起生效 | 治理机构 |
| qtdata-index.md | 经公司治理机构审议通过，自发布之日起生效 | 治理机构 + BU办公室修订 |

## 原因

这不是笔误。三组不同的生效主体反映了真实的效力层级（后经人工介入统一修复为"公司治理机构"，验证了检测的有效性）：

**最高权力机构**（四份治理类章程）
- 公司代表章程：涉及治理架构，须最高权力机构批准
- 文档格式章程：全公司统一的格式标准，须最高权力机构批准
- 离职工作章程：涉及员工法定权利，须最高权力机构批准
- 沟通管理章程：涉及全员的认知权利，须最高权力机构批准

**治理机构**（写作章程）
- 工作章程写作章程：元章程，规范围怎么写章程。它的效力层级天然低于被它定义的章程——它不能规定"最高权力机构如何批准自己"。

**治理机构 + BU办公室修订**（数据工作章程）
- 量潮数据工作章程：业务单元章程，生效需治理机构批准，但修订权下放给 BU 办公室，反映业务单元的自治权。

## 为什么这是 aha moment

传统数据融合会把这当作"数据不一致"去对齐，强行统一成同一个生效主体。但六份章程的效力主体差异不是错误，它恰好暴露了知识库中**没有显式定义但实际存在的组织效力层级**：

```
最高权力机构  ──── 批准治理类章程
     ↓
治理机构      ──── 批准元章程和业务单元章程
     ↓
BU办公室      ──── 修订业务单元细则
```

这个层级在知识库中没有任何文件显式定义——它通过效力声明的差异反向揭示出来。这就是"反向检测"的含义：不是评估知识本身的对错，而是通过结构差异发现隐含的信息。
