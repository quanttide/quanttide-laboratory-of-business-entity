# 本体评审标准

## 来源

本标准提炼自实际评审历程中暴露的反复问题。每一次评审发现的缺陷都被归纳为一条可重复使用的检测规则。

## 一、本体抽象度

本体是抽象模式，不是文档摘要。衡量本体质量的唯一标准是可复用性——换一套完全不同的文档，pattern 是否仍然适用。

### 信号检测

| 未抽象信号 | 检测方式 | 示例 |
|:----------|:--------|:----|
| 源文件引用 | pattern 中包含见 xxx.md | 见 qtdata-index 第六至九条 |
| 书名号引用 | pattern 中包含《》 | 依据《量潮科技基本章程》制定 |
| 具体角色名 | pattern 中包含岗位或身份名称 | 设三类核心岗位：项目经理、商务经理、数据工程师 |
| 具体等级编码 | pattern 中包含 L0/M1/T序列 等 | 专业序列设 L0-L3，管理序列设 M1-M5 |
| 具体数字约束 | pattern 中包含天数、字数、次数 | 限定五百字以内，答疑期不少于五个工作日 |
| 具体阶段名 | pattern 中包含流程阶段的专有名称 | 需求对接→报价签约→执行监控→验收交付→归档 |

### 自检方法

1. 跨文件检查——结构是否出现在多个源文件中。只出现在一个文件里的，不是本体
2. 去值测试——把所有角色名、阶段名、数字、条款号删掉后，剩余句子是否仍在描述一种结构
3. 换源测试——换一家完全不同的公司文档，pattern 能否直接套用
4. 填空测试——能否用 `<变量>` 标出 3 个以上可填充的槽位

### 判断标准

通过：所有信号均未命中，且通过换源测试
需修改：命中 1 个以上未抽象信号

## 二、实例归位正确性

实例是本体中变量的具体填充值。

### 检查项

- 每条实例必须标注所属的 ontology id，且该 ontology 必须存在
- 每条实例必须标注 source（源文件名）和 article（条款号）
- ontology 的 pattern 中不应包含 source_files，不应包含具体值
- 每个本体至少有 3 个实例，且来自至少 2 个不同源文件
- 实例中的具体值与源文件原文一致

### 常见问题

- 本体和实例混放：具体值写在 ontology pattern 中。修复方式：具体值移到 instances，pattern 只保留抽象结构
- 遗漏同步：源文件改了术语，实例未同步更新
- 覆盖不足：本体有多个变体但实例过少

## 三、跨域关系合理性

关系描述不同领域之间的真实连接。关系不是为了达标而编造的连接。

### 检查项

| 检查项 | 说明 |
|:------|:----|
| 真实连接 | 必须基于源文件中可追踪的引用或逻辑依赖 |
| 方向正确 | A references B 和 B referenced-by A 不是同一回事 |
| 类型准确 | governs、references、instance-of、intersects 等类型需匹配实际情况 |
| 覆盖达标 | 每个领域至少 2 条跨域关系 |

### 常见问题

- 伪关系：两个概念看起来有关系，但源文件中找不到任何引用或逻辑连接
- 方向颠倒：基础章程引用上位法 vs 上位法引用基础章程，方向含义完全相反
- 类型泛化：所有跨域关系都用 related-to，丧失语义精度

## 四、评审记录完整性

评审记录是知识库的审计追踪。没有记录等于没有评审。

### 要求

- 每个本体、实例、关系都有对应的评审记录
- 记录包含状态（通过或需修改）、意见、评审时间
- 本体重构后旧评审记录失效，须重新评审

### 记录格式

```json
{
  "biz-ops:ontology:role-responsibility": {
    "status": "通过",
    "comment": "本体重构完成，通过抽象度检测",
    "updated": "2026-05-19T21:33:09"
  }
}
```

## 评审流程

1. 跑 `python -m src.cli check-abstraction` 检测未抽象信号
2. 跑 `python -m src.cli cross-domain-report` 检查跨域关系覆盖率
3. 跑 `python -m src.cli summary` 概览各领域数据量
4. 跑 `python -m src.cli fusion-check` 检测名称冲突、引用断裂、效力一致性
5. 跑 `python -m src.cli find-undefined-terms` 检测未定义术语
6. 逐项检查实例-源文件一致性（人工）
7. 逐项评审跨域关系合理性（人工）
8. 更新 `.review.json` 记录评审结果

## 反例

以下 pattern 在一次评审中被标记为需修改：

```json
{
  "pattern": "五阶段递进流程：需求对接（产出：需求规格说明书）→ 报价与签约（产出：工作订单）→ 执行与监控 → 验收与交付 → 归档"
}
```

命中信号：具体阶段名 ×5、书名号引用 ×2。

修复后：

```json
{
  "pattern": "流程由按序执行的阶段序列组成。每阶段包含：执行角色、输入条件、活动内容、输出产物、确认关卡。阶段间通过输出→输入的链式衔接推动流程前进。"
}
```

换源测试通过。
