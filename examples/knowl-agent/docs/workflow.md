# 知识发现与建模工作流

## 核心流程

### 预备：领域发现

扫描知识库，识别所涵盖的知识领域。每个领域代表一个观察视角。

工具 → `python -m src.cli detect-domain`

```bash
python -m src.cli detect-domain tests/fixtures/input/<file>
```

基于词汇命中排序，推荐最匹配的领域。命中显著领先时规则引擎直接输出推荐；命中接近时智能体分析视角差异给人选。

产出：`tests/fixtures/output/<domain>/domain.json`（规则引擎通过 `python -m src.cli init-domain` 创建）

### 第一步：本体发现

在每个领域内找出反复出现的概念结构——知识库用哪些固定的思维模板来组织知识。本体只关心抽象模式，不含具体实例。

执行者：智能体。

核心要求：可复用性。换一套完全不同的文档，pattern 是否仍然适用？如果 pattern 中包含只在一份文档中出现过的角色名、阶段名、数字、文件引用，说明抽象不到位。

操作步骤：

1. 跨文件收集证据——在写 pattern 之前，先找至少 2-3 个来源，确认这个结构是反复出现的
2. 识别常量与变量——常量留在 pattern，变量写到 instances
3. 写 pattern——用 `<变量>` 标记可填充的槽位
4. 自检——跨文件检查、去值测试、换源测试

常见错误：

| 错误写法 | 正确写法 |
|:--------|:--------|
| 设三类核心岗位：项目经理、商务经理、数据工程师 | 以 `<职责列表>` + `<权限列表>` 成对定义 |
| 五阶段流程：需求对接、报价签约、执行监控、验收交付、归档 | 由 `<阶段序列>` 组成，每阶段含 `<执行者>` `<输入>` `<活动>` `<输出>` `<关卡>` |
| 成员有义务在传递前精炼信息，五百字以内摘要 | `<原则>` 约束 `<行为>`，违反由 `<违规模式>` 认定 |
| 专业序列设 L0-L3，管理序列设 M1-M5 | `<等级>` 递增表示资深程度递增，等级与权责正相关 |

产出：`tests/fixtures/output/<domain>/ontologies.json`

### 第二步：实例映射

将具体内容映射到本体上。

执行者：智能体。阅读文件条款，判断每条内容归属的本体。

产出：`tests/fixtures/output/<domain>/instances.json`

### 第三步：关系发现

识别跨本体或跨实例的连接。关系是本体的附属。

执行者：智能体。

产出：`tests/fixtures/output/<domain>/relations.json`

### 第四步：跨领域融合

对比不同领域对同一术语的定义和处理，暴露冲突和不一致。

工具 → `python -m src.cli fusion-check`

```bash
python -m src.cli fusion-check
```

自动检测：同名本体冲突、词汇交叉、引用断裂、效力主体一致性。

融合不是合并——不消解差异，保持各领域独立，通过对比暴露信号。

信号处理：
- 引用断裂 → 智能体判断是否需创建 stub 或更新映射
- 术语交叉 → 智能体检查含义是否一致，不一致时给人标记 **【需人确认】**
- 效力主体不一致 → 智能体分析差异并建议统一方向，给人决策

### 第五步：反馈闭环

暴露的缺口不会自动修复。智能体按能力边界处理，需要组织决策的给人。

辅助工具：

```bash
python -m src.cli validate              # 检查结构完整性
python -m src.cli summary               # 概况总览
python -m src.cli find-undefined-terms  # 找出未定义术语
python -m src.cli auto-fix              # 补缺失骨架文件
```

迭代模式：智能体修 → 跑规则引擎验证 → 再修 → 直到 validate 全部通过。

## 不做什么

- 不做格式级别的检测（标题层级、分隔线数量、用语规范）
- 不做问题追踪和评分（那是人的工作）
- 不将语言模态系统列为领域本体（应当、不得、可以是表达方式，不是概念结构）
- 不试图统一不同领域的视角差异——差异本身就是发现
