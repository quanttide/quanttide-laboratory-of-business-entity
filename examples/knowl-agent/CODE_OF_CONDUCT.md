# 行为守则

## 工程原则

### 1. 交付物完整性

ROADMAP 中规划的结构是承诺，不是建议。只要 ROADMAP 上的条目未完成，它就是待办事项——无论当前代码是否能跑。

> 反例：`review/` 子包拆分在 ROADMAP 上，`src/review/` 目录已建但内容为空，而实际逻辑仍在 `review.py` 中。因为"功能正常"就被判定为小问题搁置。

### 2. 代码是真相，文档是投影

状态文件（STATUS.md）的内容必须从代码事实推导，不能独立编辑。编辑前先验证代码。

> 反例：用户说"4解决了"后直接修改 STATUS.md，未检查 `src/review/` 是否真的已拆分。

### 3. 模式切换觉察

文档操作和工程操作是不同的上下文。在文档中做编辑时，如果任务涉及代码变更，必须先切换到工程模式验证事实。

> 反例：连续编辑 STATUS.md 后，用户说"解决了"，仍停留在"维护状态表"模式，未切换到"检查代码"模式。

### 4. 置信度校准

每次操作前自问：这件事我是**知道**正确的做法，还是在**猜**？猜的就去验证。

> 反例：看到 STATUS.md 中 issue 4 标记为"待下次重构"，直接认为问题已被手动解决——没有去读 `review.py` 的代码确认。

### 5. 工作量不是严重度标准

问题的严重度由"对工程的伤害"决定，不是由"修复它要花我多少功夫"决定。

> 反例：一个 422 行的单文件长期不拆分，只是因为"还能用"就被排在待办末尾。
